# QLPK Working Rules

## Collaboration

- Always answer in Vietnamese.
- Start from `CONTEXT.md`, `AGENTS.md`, `rule.md`, `references/ai-contract.md`, and `references/context-files.md`; classify the task and read only the required route. Do not read unrelated markdown files by default.
- Before any analysis or code, output the Task Gate from `references/ai-contract.md` and wait for scope clarity if any gate item is unknown.
- Follow the AI flow in `references/ai-contract.md`: receive, classify, route, inspect, findings, proposed solution, confirm scope, develop, QA, report, update knowledge.
- Mọi lát workflow đang làm hoặc vừa handoff phải được ghi ở đúng owner tài liệu trong cùng scope: runtime/component/data contract vào workflow map hoặc inventory, trạng thái đang làm và QA vào `references/refactor-progress.md`. Không để tài liệu tiếp tục mô tả shell, owner, UI hoặc lifecycle đã không còn đúng với source runtime.
- Do not ask for approval after only describing a problem. Provide a concrete Proposed Solution, Scope To Confirm, and QA Plan first.
- Before every code/file change request, briefly restate what you understand and the exact scope, then wait for explicit user approval (`ok`, `làm đi`, `triển khai`, or equivalent) before editing or running mutating actions. Treat this as mandatory even when the requested change looks small.
- Read existing code before proposing or editing. Let the current Flask/Jinja/jQuery structure drive the solution.
- Before proposing, mocking, or changing workflow UI, read `references/business-map.md`, `references/ui/information-architecture.md`, `references/ui/design-from-data-checklist.md`, and the screen workflow/data-inventory maps under `references/workflows/` when they exist.
- Prefer small, reversible changes. Avoid broad refactors unless they are required for the requested behavior.
- Do not revert, overwrite, or delete user work. If a file has unrelated changes, work around them.
- Use `apply_patch` for manual file edits.
- UI QA is mandatory for every UI-facing change. Static/code checks are not enough for UI work. After changing HTML/CSS/JS that affects rendering, controls, layout, modals, dropdowns, calendars, tables, forms, notifications, or shared shell components, open browser verification yourself and inspect the affected screen before reporting done. Browser/UI verification is agent-led by default for UI work and may use Chrome, the in-app browser, Playwright/headless browser tooling, or an equivalent local browser path when the environment allows it.
- Treat UI QA as an independent review, not a rubber stamp for your own patch. Verify the actual rendered DOM and screenshot against the requested behavior, then look for regressions around alignment, spacing, typography, color contrast, overflow, clipping, scrollbars, disabled/loading states, z-index/backdrop layers, responsive breakpoints, console errors, failed assets, and stale/duplicated UI branches. If any visible issue remains, fix it before reporting completion.
- Do not report `xong`, `đã ổn`, or `pass` for UI work until both static validation and browser/visual QA have passed. If the user explicitly asks to skip browser testing, or browser QA cannot run because the server, auth, data, or environment is unavailable, explicitly report `chưa pass visual QA`, state what was validated, and ask for the missing condition instead of presenting the UI as complete. Do not leave browser validation sessions running unnecessarily.
- Before changing layout, write the visual acceptance states and trace the full constraint chain: shell/parent height and overflow, section, grid/flex item, list/table child, then scroll/pagination control. Never patch a child-only selector for blank space, clipping, height, scrollbar, or alignment before this trace is complete.
- Browser QA must use the states that expose the change: empty plus populated, sparse plus dense/long data for a list/table, and every changed interaction. A hidden panel, empty queue, or fixture without the relevant control may verify markup/assets only; it cannot pass visual or interactive QA. If an actual state is unavailable, name it precisely as `chưa pass visual/interactive QA` and do not call the feature finished.
- A control that only renders is not acceptable by itself. Validate its operational scale: pagination must reach the required page set without impractical repeated clicks; scroll must belong to the intended region without creating blank panels or page-level overflow; paired regions must not force unrelated empty space.
- For restructuring work, follow `so-do-to-chuc.md`: one vertical workflow slice at a time, with explicit contract and validation.

## Implementation Discipline

- Keep backend, frontend, model, schema, migration, and template changes aligned.
- Keep folder structure changes tied to a concrete workflow improvement, not cosmetic cleanup.
- Avoid hardcoding clinical state, IDs, names, permissions, and workflow transitions in frontend logic when the backend can provide them.
- Prefer existing helper APIs and local patterns over new abstractions.
- Preserve Vietnamese labels and domain language already used by the product.
- Keep comments sparse and useful. Add comments only for non-obvious behavior or fragile contracts.

## Frontend Rules

- Frontend stack is Jinja + Bootstrap + jQuery + plain JavaScript. Do not introduce a SPA framework.
- Workflow UI must be designed from actor/task and data owner, not from isolated database fields. For every new or changed UI block, identify the business task, source API, canonical owner table, editable/read-only state, component owner, clear/reset owner, and whether the information is visible immediately, collapsed, modal-only, or not shown. If a workflow has a data inventory, every visible field must trace back to it or the inventory must be updated first.
- Reuse existing CSS files and DRY components before adding new styles. Shared UI primitives must have one owner: app header, dry/sidebar navigation, workspace shell/tabs/app launcher, common controls, shared modals, typography/colors/spacing tokens, and repeated layout patterns belong under the shared/template/component/app-shell layers. Pages may compose/configure these primitives and add workflow-private styles, but must not copy shared HTML/CSS/JS into many templates or create page-local clones of common controls.
- Do not treat CSS/HTML fixes as cosmetic guessing. Before changing FE, inspect the current DOM, owner file, cascade order, selector specificity, token source, and JS/runtime classes involved. Make a code-evidence-based judgment, then fix the owner or contract. Do not use stacked overrides, duplicated selectors, page-local patches for shared primitives, or `!important` as the default solution; `!important` is allowed only when overriding a third-party/library rule or an existing legacy rule cannot be removed in the same safe slice, and the reason must be obvious from nearby code or the final report.
- Do not "pump CSS" to hide frontend bugs. If a UI element is positioned, clipped, duplicated, or not closing correctly, fix the DOM/JS/component lifecycle owner first; add CSS only when the visual contract itself needs styling.
- Do not solve a layout symptom in isolation. For every scrollable, paginated, or split region, identify which ancestor owns its available block size and which sibling can stretch it before choosing a child `max-block-size`, `overflow`, or grid rule.
- UI state must have one authoritative owner. Do not keep old and new branches running together with unclear fallback logic such as "if not A then B" when both branches can still render, open, save, or mutate state. If development exposes overlapping old/new branches, duplicated owners, stacked CSS/JS fixes, runtime measurement patches, or conflicting fallback paths, remove the duplicate branch and leave one source of truth in the same safe slice. If removal is risky, changes production behavior, or the correct owner is uncertain, stop and report the exact conflict/risk to the user for a decision. Do not add a third branch, extra override, observer/timer workaround, or compatibility shim on top of the old conflict unless the user explicitly accepts that temporary debt. For async UI components such as autocomplete/dropdowns/modals, the owner must invalidate stale requests on focus/close/dispose and verify the current lifecycle token before rendering. A stale response must be ignored, not allowed to reopen or overwrite the active field.
- Tuyet doi khong boc khung lung tung in operational screens. A visual region must have exactly one frame owner; do not stack border/card/wrapper layers around each other, and do not wrap a component in another bordered card when the component itself is already the block, table, panel, or card. If a region already has a clear boundary, inner groups should use whitespace, section headings, lightweight dividers, surface contrast, or semantic controls instead of another full border and radius. Full borders are reserved for primary region boundaries, interactive controls, tables/lists that need containment, upload dropzones, status/vital tiles, or modals. Before adding a border or wrapper, identify the owner, prove it communicates structure, and avoid adding visual noise.
- Keep action buttons compact and icon-based where existing screens use that pattern.
- Icon/action/notification UI must use the shared semantic icon system when touched: `app/static/css/shared/icon-tokens.css`, `app/static/css/shared/feedback-tokens.css`, and `app/static/js/shared/icon-system.js`. Do not keep inventing raw `btn-outline-primary` / `btn-outline-danger` action buttons or arbitrary Bootstrap icon choices for repeated table actions; use `QLPKIconSystem.renderActionButton()` plus semantic classes like `qlpk-icon-action--view|edit|delete|transfer|download|save` and feedback types `success|info|warning|error|critical` so colors, icon weight, hover/focus, tooltip, and accessibility stay consistent. Icon+text buttons must use `QLPKIconSystem.renderIconTextButton()` or `.qlpk-icon-text-button` with `.qlpk-button-icon`, and icons inside buttons must inherit `currentColor` instead of setting their own color. Source icons, file icons, section icons, and feedback icons must use the shared registry/classes (`qlpk-source-icon`, `qlpk-file-icon`, `qlpk-section-icon`, `qlpk-feedback-icon`) when touched; do not hardcode new per-page icon palettes for the same meanings.
- Badge/toast/feedback colors must follow semantic meaning, not decoration: save/success/completed action feedback is green, delete/error/failure is red, warning/needs-attention/draft is yellow, neutral/info workflow state uses neutral or info tokens. Use `feedback-tokens.css` variables instead of one-off badge colors.
- Toast và cảnh báo thao tác phải ngắn, thực dụng và thuộc owner workflow: câu đầu nêu điều vừa xảy ra, câu sau nêu hành động người dùng cần làm. Không đổ nguyên `error.message`, danh sách lỗi backend, stack trace hoặc từ kỹ thuật như `module`, `component`, `server`, `appointment ID` vào toast; chi tiết chẩn đoán giữ ở log hoặc vùng chi tiết phù hợp. Không ghép thêm tiền tố `Lỗi:`/`Hướng dẫn:` khi icon, màu và nội dung đã thể hiện ngữ nghĩa.
- `app/static/js/shared/user-feedback.js` (`window.QLPKUserFeedback`) là renderer feedback duy nhất. Template tương tác phải include `partials/user-feedback-runtime.html`; workflow được giữ wrapper tương thích nhưng wrapper chỉ được ủy quyền cho owner chung. Không tạo lại Bootstrap toast container, page-local toast DOM/CSS hoặc hiển thị raw response. Chạy `python3 scripts/check_user_feedback_contract.py` khi chạm notification/error handling.
- Every frontend change must preserve the global FE debt gate: run `python3 scripts/check_frontend_contract.py` or `python3 scripts/smoke_health.py` before reporting done. The gate is strict-zero for cleaned categories and baseline-locked for legacy debt; counts may go down but must not go up. Do not raise a baseline to make a change pass unless the user explicitly accepts a new technical debt item with a reason.
- When touching the receptionist screen, run `python3 scripts/check_receptionist_fe_contract.py` before reporting done. This check blocks removed local patient-search/modal/hidden-control bridges and raw Bootstrap action buttons from returning to the cleaned receptionist scope.
- Do not create landing-page style UI for operational screens.
- Do not create UI mockups by randomly selecting fields from models/API payloads. A mockup is only valid when it follows `references/ui/design-from-data-checklist.md` and can trace every visible field back to business need and owner.
- For date inputs, prefer the existing Flatpickr setup and Vietnamese formatting helpers.
- Typography must use shared CSS tokens from `app/static/css/shared/typography.css`: `--qlpk-font-family` is Roboto; font sizes must use the `--qlpk-font-size-*` scale; font weights must use `--qlpk-font-weight-regular|medium|semibold|bold`. Do not add page-local `font-family` stacks or hardcoded `font-size` / `font-weight` values in CSS or generated inline style strings. Canvas/chart libraries may keep numeric `fontSize`/`fontWeight` config only when the library requires numbers.
- Text color must be readable to a normal human eye, not merely decorative. Do not use pale, low-contrast text for labels, empty states, buttons, dropdown actions, badges, table metadata, or secondary descriptions, especially on cream/white surfaces. Normal text should meet at least WCAG AA contrast (`4.5:1`), large/icon text at least `3:1`; muted text is allowed only when still clearly legible. Disabled controls may look inactive, but their label must remain understandable. Avoid combinations like faded beige/gold text on cream backgrounds for actionable UI such as notification buttons.
- Shared shell/header/tab UI must be compact and content-driven. Default small controls should use tight spacing around `5px 10px`; do not use large padding, decorative card spacing, or fixed/min heights such as `72px` unless a concrete layout constraint requires it.
- Ongoing FE redesign is mobile-first. Build the small viewport layout first, then enhance for tablet/desktop. A responsive solution must not simply hide overflow or force users into long internal scroll panels; for dense navigation use tabs, segmented groups, accordions, or progressive disclosure before accepting scroll as a fallback. New responsive component layout must use tokens, `rem`, `%`, viewport units, `clamp()`, `minmax()`, and content-driven grid/flex sizing; do not hardcode component dimensions/breakpoints in `px`.
- Receptionist layout contract is strict: `Danh sach cho chuyen kham` and `Tiep nhan benh nhan` are paired columns inside one viewport-height workspace panel. The intake column and queue column must both be `100%` of that panel height; long queue/form content scrolls inside the corresponding column/body. Do not let either column stretch the whole page row, do not use JS-measured pixel heights, and do not leave blank right-panel space caused by the queue list pulling the layout taller.
- Shared app header is the current primary navigation shell: full-width header with Sơn Tâm brand, global command search, app launcher, notification/calendar icons, account menu, and workspace tabs. It must not include a sidebar collapse button. Keep base header padding at `6px 20px`, use the Sơn Tâm website identity with a dark chocolate header (`#4b2719`, `#5a301f`, cream text `#fffaf3`, gold accent `#d6a069`) and warm cream content surfaces (`#fffdf9`, `#fbf8f2`, `#f8f1e9`, text `#352821`). Keep the brand/logo plus app launcher visually prominent without turning the header into a floating banner/card. `qlpkGlobalSearchInput` is patient-first: search returns matching patients, clicking a patient selects it and loads that patient's examination history below; it must not show medicines/documents or mixed appointment search results. Copy/open-history actions must be explicit buttons, not row-click side effects. Backend must provide explicit action metadata by role, and page JS should expose small `QLPKGlobalSearchActions` bridges instead of inferring clinical behavior from display text.
- Do not set `min-height` on shell controls, tabs, launcher tiles, cards, or panels just to make them look spacious. Use natural content height, explicit icon/input dimensions, or flex layout constraints; `min-height: 0` is acceptable only as a technical flex/scroll fix.
- Workspace navigation tabs must preserve open page state. Switching between already-open functions should show the existing workspace surface, not reload the page or open a browser tab. Persisted tab and active-tab state is owned by the authenticated user id and restored only for that owner; stored configured routes must be filtered through the current permission set before render/subscription. On top-level direct load/reload, the active tab must match the browser URL's native page; stale workspace state must not hide `#qlpkWorkspaceNativePane` and produce a blank screen. Closing a native tab while another tab remains must navigate the top-level URL to the selected remaining tab after the leave guard approves, so the closed native route cannot be recreated on reload. If an iframe tab cannot produce an active pane, fall back to the native pane for the current URL.
- After UI work, run terminal-safe validation such as CSS/JS syntax checks, `scripts/smoke_health.py`, static reference checks, and targeted HTTP checks, then run browser/visual QA on the affected workflow. For third-party widgets such as Flatpickr, FullCalendar, Bootstrap modals/dropdowns, SweetAlert/custom confirmations, autocomplete controls, and table/list renderers, verify the component visually after every CSS/DOM change because syntax/contract checks cannot prove layout integrity.

## Backend Rules

- Authentication is JWT-based. Protected endpoints should use the existing `require_auth` pattern unless the endpoint is intentionally public.
- Database access uses `get_db()` / `SessionLocal`; close sessions in `finally` blocks.
- `main.py` registers many blueprints and initializes tables on import. Avoid casual imports of `main.py` during checks.
- Use SQLAlchemy models and existing serializers/helpers instead of duplicating raw JSON mapping.

## Data Source Rules

- Patient demographics and lifetime history belong in `patients`.
- Appointment scheduling/admin data belongs in `appointments`.
- Per-visit clinical data belongs in `examinations`.
- Flexible modal/detail fields belong in `examination_details` with the correct section name.
- Prescriptions belong in `prescriptions` / `prescription_items`.
- Orders/clinical indications belong in `chi_dinh` and order catalog tables.

Read `references/data-contracts.md` before changing any of these boundaries.

## High-Risk Areas

- `app/static/js/doctor-examination.js` is large and stateful. Read `references/doctor-examination-context.md` before touching it.
- `app/api/appointment.py` is a central save/update endpoint and affects several screens.
- `app/utils/examination_utils.py` controls section mapping for doctor vs psychologist detail fields.
- Prescription, inventory, payment, Google Calendar, and survey scoring have side effects; trace from frontend caller to backend writer before changing.
